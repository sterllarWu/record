业务问题与系统目标

主机权威数据在配置平台，作业下发在作业平台，巡检「查谁、查什么、何时查」原先散落在表格和个人习惯里。计划配完经常无法在目标机上真正跑起来；多个业务共用一套登录入口时，A 业务的人可以看到或操作 B 业务的对象；执行明细入库之后，仍然要逐台、逐项点开才能形成初判。

系统目标是在现有蓝鲸能力之上交付一台可在预发布演示的巡检 SaaS：业务运维在自己的权限范围内圈定主机、编排方案与计划、经作业平台真实执行、结果结构化入库，并在已有证据上做只读归纳。智能体不能改配置、不能触发执行，处置由人确认。

导师只提出「加入 AI 研判」。加在哪个界面、证据从哪里取、模型能不能写操作，全部由本人决定。本人完成场景选择、方案取舍、应用注册、网关授权、智能体创建、预发布部署，以及 Django / DRF / Celery / Vue 3 主路径实现与联调。实现阶段使用编程助手起草代码，对象模型、鉴权边界和 AI 边界由本人确认。

配置平台、作业平台、权限中心、监控、智能体平台、PaaS 与开发框架是已有能力，本人在其上做 SaaS 侧模型、接口、异步任务、前端主路径和接入联调。

验证范围：有权限的测试集群 38 台主机；系统尚未正式上线；除本人外约 3 名内部使用者走过主路径。这是验证范围。

本人负责的模块

  • 对象：查询即缓存、标签、主机组、方案、计划、执行记录。
  • 执行：按巡检项类型在后端生成脚本、提交作业、Celery 轮询、结构化等级入库。
  • 权限：按业务隔离读写与执行；权限服务异常时写与执行拒绝。
  • AI：计划分析、执行总结、基于上次结论的追问；证据先鉴权再送模型。
  • 接入：应用注册、网关授权、智能体创建、预发布部署、请求追踪头。

集成关系与端到端链路

浏览器里的 Vue 3 页面只负责选择业务、编排对象、展示历史和发起只读分析。真正的脚本内容、作业凭证、鉴权判定、证据打包都在 Django 后端完成。Celery 负责作业状态轮询和主机缓存同步，避免 HTTP 请求一直占着。

flowchart TB
  U[业务运维 / 只读用户] --> FE[Vue 3 前端]
  FE --> API[Django + DRF]
  API --> IAM[权限中心]
  API --> CMDB[配置平台]
  API --> JOB[作业平台]
  API --> CEL[Celery 轮询与同步]
  API --> AGENT[智能体 只读]
  FE --> TRACE[追踪头]
  API --> TRACE

一次完整手动巡检按下面顺序发生：

  1. 用户选择有权业务，查询主机。查询结果写入本地缓存，后续编排使用缓存对象，后台仍会定时全量同步配置平台。
  2. 用户用标签、主机组或筛选条件圈定「查谁」，用方案圈定「查什么」（巡检项与阈值）。创建计划时把方案打成快照。
  3. 用户触发执行。后端解析目标主机，按项类型生成脚本，带着当前登录身份提交作业平台。前端不传任意命令，不传执行凭证。
  4. 接口立即返回执行单。Celery 轮询作业状态与日志，解析约定前缀行，按阈值写入正常 / 预警 / 严重 / 出错。
  5. 部分主机失败时整次记为部分失败，已经成功的项照常展示。
  6. 用户在计划页做分析，或在历史页做该次总结，或在浮窗里基于上次结论继续追问。模型返回带计划标识、执行标识、主机标识的文字。人决定要不要改阈值、重跑或去作业平台处理。

对象模型：查询即缓存、方案快照、目标弱引用

配置平台是主机权威来源。SaaS 每次查询都把结果写入本地，是为了让标签、主机组、方案、计划可以稳定引用同一套主机主键，避免编排过程中反复打配置平台、也避免计划保存时主机列表漂移到未知状态。缓存会过期、也会被定时任务全量刷新。

「查什么」和「查谁」拆开存储。创建计划时，方案（巡检项、阈值、脚本类型）做深拷贝，成为该计划自己的快照。之后有人改方案模板，已有计划仍按快照执行。要把计划改成新模板，必须走显式「同步方案」。这样做的目的：历史执行始终对应当时那套检查项，回看时能解释「那一次到底查了什么」。

「查谁」保存组、标签或筛选条件，执行当下再解析成主机列表。组成员变化、标签调整之后，下一次执行会带上新成员。快照锁住检查内容，弱引用跟随资产变化，两件事同时成立。

flowchart LR
  SUITE[方案模板] -->|创建计划时深拷贝| SNAP[方案快照 查什么]
  GRP[主机组 / 标签 / 筛选] -->|执行时解析| HOSTS[主机列表 查谁]
  SNAP --> PLAN[巡检计划]
  HOSTS --> PLAN
  PLAN --> RUN[执行单]

受控脚本、异步轮询、状态与超时

脚本由后端按巡检项类型拼接固定模板。用户在页面上选「磁盘使用率」「进程存活」这类项，并填写阈值，不能贴一段任意 Shell。作业平台所需的执行身份留在服务端，浏览器拿不到。输出里只有带约定前缀的行会进入结构化解析，其余日志丢弃，减少把无关输出当成指标。

触发执行的 HTTP 接口只做：鉴权、解析目标、提交作业、写入执行单（状态为等待或执行中）。轮询放在 Celery。轮询上限大约 20 分钟，到期把执行单标为超时。Worker 任务硬超时大约 25 分钟，避免进程一直占着。定时巡检在代码里已用调度扫描启用了 Cron 的计划并写成「定时」触发类型；预发布运行证据待确认，此处不写成已经在预发布跑通过。

  等待 --> 执行中

终态可以按权限回看和重跑。单条结果另有等级：正常、预警、严重、出错。部分失败表示至少一台主机或一项检查没有成功，其余成功项仍然可读。

安全与失败行为

  • 证据只取当前用户已经有权看见的计划、执行和结果。不可信日志加边界后再进提示词。
  • 口令、票据一类样式在送模型前替换。作品集不展示真实脱敏样例。
  • 智能体侧没有 SQL、没有 Shell、没有作业提交工具。不能执行计划、不能同步方案、不能改阈值。
  • 证据不够时，回复必须说明证据不够。智能体未配置、网关失败、超时（对话默认 75 秒）返回明确错误，页面不伪造一段「看起来像分析」的文字。
  • 仓库里有与解析、脱敏相关的测试代码，不作为本人已经完成的单测验收。提示词注入的人工页面验收尚未做。没有评测集，没有准确率数字。

部署、可观测、排障原则

预发布环境由本人完成应用注册、网关授权、智能体创建和部署。部门内可以走通：查询主机、手动执行、运维与只读两套权限、计划分析、执行总结、追问。

请求带追踪头，便于在监控里按一次点击反查调用链。服务提供健康与接入自检，用来核对「平台注入的环境变量名」和「框架实际读取的名字」是否一致。接入可观测时出现过：指南里的占位符被原样写进配置、注入变量前缀与框架读取前缀不一致、服务名为空导致上报无处归属。处理方式是在健康接口打出 enabled、采样、上报地址是否存在等布尔与长度信息（不在对外材料里写内部参数），再逐项改配置直到监控里能看到这条应用。

作业链路里，接口能调通不等于能代表当前登录用户下发。需要在线请求携带登录态，并且该用户对目标业务具备作业访问权限。从线程上下文里「碰巧还有用户」在预发布上会丢身份。脚本生成留在后端，也是为了让这条身份链路只有一条。

智能体接入时，文档示例的调用方式和现网成功响应的字段布局需要当场核对。成功时顶层状态字段可能是固定成功文案，分析正文在别的字段里。如果把状态字段当成正文，页面会只显示一个成功字样。处理方式是按现网真实结构取正文，并在测试代码里覆盖「不要把成功态当成回答」（该测试不作为本人已完成验收的声明）。

情况系统行为当前验证
权限服务异常写与执行拒绝按此实现；无权限账号未试
作业超时 / 部分失败超时态；分主机、分项等级手动执行主路径已走

若继续开发

  • 固定一批脱敏样本：必须出现的计划/执行/主机标识、必须拒绝的越权请求、必须说明证据不足的情况。
  • 产品埋点：打开分析的次数、证据不足占比、看完分析后是否回到原执行、是否随后重跑。
  • 在预发布执行历史里确认「定时」记录之后，再对外宣称调度闭环。
  • 主机级细粒度授权、结果通知、巡检成功率业务看板未作为本次主交付。
